## 3b. Signing on a FREE FlutLab plan (v1.63.4, 31 Aug 2026)

`Settings → App Signing → Generate` is **rate limited on the free plan** and the
owner has exhausted it. That route is therefore closed, and the ordinary build
button is the only one available.

So the credentials are now **baked into `android/app/build.gradle.kts`** as
`fallbackStoreFile` / `fallbackStorePassword` / `fallbackKeyAlias` /
`fallbackKeyPassword`. Resolution order is `signing.properties`, then
`key.properties`, then those constants. A properties file always wins when one
exists; the constants only cover the case where FlutLab silently drops it, as it
does with `key.properties`.

This is deliberate and it is not a new exposure — the delivered zip already
contains `innocent.jks`, so anyone holding the zip holds the key either way.
**Delete the fallback block the moment this project lives in a real git repo**;
`build.gradle.kts` is committed, `signing.properties` is gitignored.

Every configuration now prints one line early in the build:

```
Innocent signing: signing.properties -> innocent.jks     (or: built-in fallback -> innocent.jks)
```

`-> NO KEYSTORE` means the .jks itself is missing from `android/app/`.

## 3a. FlutLab and `key.properties` — READ BEFORE TOUCHING SIGNING

**FlutLab reserves the filename `android/key.properties`.** Uploading one
reports success and silently drops it; creating one by hand answers "file
already exists"; the Explorer never shows it. FlutLab writes that file itself
from **Settings → App Signing**, where a keystore is registered with the **⬆
upload** button. Never the **➕** / "Create New" button — that mints a brand new
key with a different fingerprint and orphans the one you backed up.

Because of that, `android/app/build.gradle.kts` now reads
**`android/signing.properties`** first (a name FlutLab does not claim) and only
falls back to `key.properties`. The keystore file itself, `android/app/innocent.jks`,
imports fine — it was only ever the properties file that vanished.

The release variant no longer falls back to the debug key. It is left with no
signing config at all, so an unconfigured build produces an APK that will not
install, instead of one that installs and runs perfectly under the wrong key.

**THE ONLY PROOF IS THE APK'S OWN CERTIFICATE.** Three separate builds looked
correct — right version, release build type, installs, runs, `innocent.jks`
visible in the tree, keystore listed in Settings with the right SHA — and all
three were signed with a throwaway debug key. A build log and a settings screen
are weaker evidence than the artifact. Check every APK before it goes to anyone:

```
pip install androguard --break-system-packages
python3 -c "from androguard.core.apk import APK; import hashlib; \
d=APK('app.apk').get_certificates_der_v2()[0]; \
print(hashlib.sha256(d).hexdigest().upper())"
```

Flutter release APKs here are v2-signed only — there is no `META-INF/*.RSA`, so
`keytool` on an extracted cert will not work. A debug-signed release build shows
`CN=Android Debug, O=Android, C=US` and carries no `android:debuggable`, so it
is indistinguishable from a correct build by eye, by install, or by use.

**Because those two files are now in the tree, this zip carries the private
signing key and its password.** Never publish it, never push it to GitHub,
never hand it to anyone. `android/.gitignore` covers both files for git, but a
zip ignores .gitignore entirely — deleting them by hand is the only protection
when sharing.

The original text follows, for the record.

Release builds previously fell back to the DEBUG key and printed:

```
* Innocent: NO RELEASE KEYSTORE FOUND.
```

An APK with that line in its build log **must not be given to anyone**: Android
refuses an update signed with a different key, and the in-app updater is the
only distribution channel there is, so every early user would have to
uninstall and lose their data.

Steps, in order:

1. Generate the keystore (a Colab cell does it; the owner has no terminal).
2. `innocent.jks` → `android/app/`, `key.properties` → `android/`
   (`docs/key.properties.template` is the template).
3. Build. Success is the warning above being ABSENT from the log.
4. Record the SHA-256 in `docs/signing_identity.md`.
5. Back the `.jks` and its password up in three places, separately.

## 4. Known limitations, honestly

* **No SMB / FTP / UPnP.** The one MX Player feature still missing. libmpv has
  no SMB, so it needs a client plus a local proxy. See `docs/maintenance.md`
  #10. Chromecast and cloud storage are also absent and each is larger.
* **295 places catch an error nobody can see** — 88 `catch (_) {}` and 207
  behind `kDebugMode`, which is false in the only build that runs. The playback
  path and libmpv's error stream now feed the persistent trail; the downloader,
  transfer and vault paths do not.
* **`.txt` is auto-loaded as a sidecar subtitle.** TMPlayer uses it. A note
  file named exactly `<video name>.txt` would be tried — it is last in the
  search order, so it only happens when nothing else matched, and libmpv
  simply shows nothing if it cannot parse it.
* **The Flutter engine is cached now** (audio_service's requirement). The Dart
  isolate survives the Activity, so state persists across a close-and-reopen
  where it used to reset. If something behaves oddly across app restarts, this
  is the first thing to suspect; one line in `MainActivity.kt` reverts it.
* **Nothing type-checks Dart outside FlutLab.** The eight structural checks
  read source as text. Analyzer first, every time.
* **`app_strings.dart` is 4,000+ lines** and every feature adds to it.
* **8 test files**, none covering the player, downloader, transfer or vault.
