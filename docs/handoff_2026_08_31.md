## 3. THE DOCUMENT BUG THAT WOULD HAVE COST A DAY

`docs/client_api_contract.md` listed the catalogue columns as
`...,popularity,access_tier`. The app actually asks for `view_count`,
`photo_count`, `video_count`, and filters on `is_featured`. A `titles` table
built from the old document answers **every** catalogue call with HTTP 400, and
**an empty catalogue and a failed fetch look identical on screen** — so the
symptom would have been "the Movies tab is blank" with nothing to go on.

The document is corrected. More usefully, `docs/movies_step3_supabase.sql` is
derived from `api_content_repository.dart` itself, and a script checked column
for column that the SQL grants exactly the fifteen the app selects, plus
`is_featured`, and never `locator`.

### Three defects found and fixed while writing that SQL

Worth recording, because all three parse cleanly and fail later:

1. `get diagnostics x = row_count` assigned into a **boolean**. Postgres has no
   integer→boolean assignment cast, so `record_view` would have thrown on the
   first view ever recorded. Now an `int`.
2. `landing_rows` built its rows with `union all`, which guarantees **no
   order** — the landing page could put "Recently added" above "Trending" on
   one call and below it on the next. Now ordered by an explicit ordinal.
3. `row_catalogue` returned `setof json`. The app sends the filter bar's
   parameters in the same query string, and PostgREST applies them as filters
   on the result — against a single scalar column, `year=eq.2024` fails with
   "column year does not exist". Returning `setof titles` would have been
   filterable and **worse**: function output rows are computed, so the column
   grants would not apply and `locator` would be selectable. Fixed with a
   `title_cards` view holding exactly the safe columns.

### And one in the function

`encodeURIComponent` does not encode `! ' ( ) *`, but SigV4 requires strict
RFC 3986. A key like `v/2026/my title (HD).mp4` would sign one string and
request another, and R2 would answer `SignatureDoesNotMatch` — for that title
only, while every plainly-named title played perfectly. Found by testing the
signer against an independent implementation with a realistic filename, not by
reading it.
